# Система учёта заявок на командировки

## Назначение

Приложение предназначено для учёта сотрудников, служебных
поездок, заявок на командировки и результатов их согласования.

В ПР3 была реализована консольная версия с классами
предметной области и хранением данных в JSON.

В ПР5 добавлен веб-интерфейс на Django: страницы просмотра
данных, статистика, навигация и обработка ошибки 404.
Дополнительно реализованы формы создания и редактирования
сотрудников и заявок.

## Целевая аудитория

Сотрудники организации, которые оформляют командировки,
и руководители, которые рассматривают заявки.

Регистрация, авторизация и разграничение прав доступа
в текущей версии не реализованы.

## Используемые технологии

- Python 3.10 или новее;
- Django 5.2;
- HTML;
- CSS и Bootstrap 5.3;
- Django Forms;

## Предметная область

Основные сущности:

- сотрудник;
- поездка;
- заявка на командировку;
- согласование.

Сотрудник может иметь несколько заявок. Каждая заявка
связана с одним сотрудником, одной поездкой и одним
согласованием.

Основные правила:

- дата окончания поездки не может быть раньше даты начала;
- расходы и лимит бюджета не могут быть отрицательными;
- при одобрении стоимость поездки не должна превышать бюджет;
- у сотрудника не может быть одобренных поездок
  с пересекающимися датами;
- сотрудника со связанными заявками нельзя удалить;
- при редактировании заявки сохраняются её номер и статус;
- изменение одобренной заявки требует повторной проверки
  бюджета и пересечения дат.

## Возможности веб-интерфейса

### Главная страница

Отображает:

- количество сотрудников;
- общее количество заявок;
- количество одобренных заявок;
- общую стоимость одобренных поездок.

Переходы в разделы находятся в верхней навигации.

### Сотрудники

- просмотр списка сотрудников;
- просмотр карточки сотрудника;
- просмотр связанных заявок;
- добавление сотрудника;
- изменение ФИО и должности;
- удаление сотрудника без связанных заявок.

Удаление выполняется на странице редактирования
и требует подтверждения в браузере.

### Заявки

- просмотр списка по дате начала поездки;
- просмотр карточки заявки;
- создание заявки;
- редактирование заявки;
- выбор сотрудника из списка;
- просмотр дат, продолжительности и расходов;
- отображение статуса согласования.

Новая заявка получает статус «на рассмотрении».

Редактирование сохраняет статус заявки. Одобрение
и отклонение выполняются в консольной версии.

## Возможности консольной версии

Консольное приложение ПР3 сохранено.

Оно позволяет:

- добавлять и просматривать сотрудников;
- создавать и просматривать заявки;
- искать заявки сотрудника;
- сортировать заявки по дате;
- рассчитывать продолжительность и стоимость поездки;
- одобрять и отклонять заявки;
- проверять бюджет и пересечение дат;
- просматривать статистику;
- загружать и сохранять данные.

## Основные классы

### Employee — сотрудник

Файл: `models/employees.py`.

Атрибуты:

- `id` — идентификатор;
- `name` — ФИО;
- `position` — должность.

Конструктор проверяет обязательные данные.
Метод `__str__()` возвращает строковое представление.

Функции:

- `add_employee()` — создание сотрудника и добавление в список;
- `find_employee()` — поиск сотрудника по идентификатору.

### Trip — поездка

Файл: `models/trips.py`.

Атрибуты:

- `destination` — место назначения;
- `purpose` — цель поездки;
- `start_date` — дата начала;
- `end_date` — дата окончания;
- `travel_cost` — стоимость проезда;
- `hotel_cost` — стоимость проживания за поездку;
- `daily_allowance` — суточные за день.

Методы:

- `calculate_days()` — расчёт продолжительности;
- `calculate_total_cost()` — расчёт общей стоимости;
- `overlaps()` — проверка пересечения дат;
- `__str__()` — строковое представление.

Продолжительность включает день начала и день окончания.

Общая стоимость рассчитывается как сумма проезда,
проживания и суточных за все дни поездки.

### Approval — согласование

Файл: `models/approval.py`.

Атрибут `status` хранит состояние согласования.

Методы:

- `decide()` — одобрение или отклонение;
- `__str__()` — текстовое представление статуса.

Конструктор допускает статусы «на рассмотрении»,
«одобрена», «отклонена» и «отменена».

Отдельная операция отмены заявки в интерфейсе
не реализована.

### TravelRequest — заявка

Файл: `models/travel_requests.py`.

Атрибуты:

- `id` — номер;
- `employee` — объект сотрудника;
- `trip` — объект поездки;
- `approval` — объект согласования;
- `budget_limit` — лимит бюджета.

Методы:

- `approve()` — проверка правил и запись решения;
- `__str__()` — строковое представление.

Функции модуля:

| Функция | Назначение |
|---|---|
| `create_request()` | Создание заявки |
| `find_request()` | Поиск по номеру |
| `find_requests_by_employee()` | Поиск заявок сотрудника |
| `sort_requests_by_date()` | Сортировка по началу поездки |
| `get_request_statistics()` | Расчёт статистики |

## Взаимодействие объектов

Объект `TravelRequest` содержит ссылки на объекты
`Employee`, `Trip` и `Approval`.

При загрузке заявки сотрудник находится по `employee_id`.
Поездка и согласование создаются из вложенных данных JSON.

Веб-представления используют существующие классы
и функции ПР3. Расчёты выполняются методами предметной
модели.

## Обработка HTTP-запросов

Просмотр страниц выполняется через GET-запросы.

Создание, изменение и удаление данных выполняются
через POST-запросы.

Маршрутизация распределена между корневым `urls.py`
и файлами `urls.py` приложений.

View-функция получает объект запроса, загружает данные,
вызывает предметную логику и возвращает HTTP-ответ.

После успешного сохранения выполняется перенаправление,
чтобы обновление страницы не повторяло отправку формы.

## Формы

В `employees/forms.py` находится `EmployeeForm`.
Она содержит ФИО и должность.

В `trip_requests/forms.py` находится `TravelRequestForm`.
Она содержит выбор сотрудника, данные поездки,
расходы и лимит бюджета.

Формы проверяют обязательные поля, даты и числовые
значения. Дополнительные предметные проверки выполняются
классами ПР3.

В POST-формах используется CSRF-токен.
Проверку выполняет `CsrfViewMiddleware`.

## Хранение данных

Данные предметной области находятся в:

- `data/employees.json`;
- `data/requests.json`.

Сотрудник сохраняется с полями `id`, `name`, `position`.

Заявка содержит:

- номер;
- `employee_id`;
- вложенные данные поездки;
- общую стоимость;
- лимит бюджета;
- статус согласования.

Даты сохраняются строками формата `ГГГГ-ММ-ДД`.

Основные функции `storage.py`:

| Функция | Назначение |
|---|---|
| `load_data()` | Чтение списка из JSON |
| `save_data()` | Запись списка в JSON |
| `load_employees()` | Создание объектов сотрудников |
| `save_employees()` | Сохранение сотрудников |
| `load_requests()` | Создание заявок и связанных объектов |
| `save_requests()` | Сохранение заявок |

При загрузке JSON преобразуется в объекты Python.
При сохранении объекты преобразуются в словари.

Веб-версия строит пути к файлам относительно
`settings.BASE_DIR`.

База SQLite используется для служебных таблиц Django.
Сотрудники и заявки продолжают храниться в JSON.

## Обработка ошибки 404

Для отсутствующего сотрудника или заявки представление
явно возвращает `HttpResponse` со статусом 404.

Для неизвестного URL в корневом `urls.py` настроено:

```python
handler404 = "homepage.views.page_not_found"
```

Для проверки общего обработчика:

1. Установить `DEBUG=False`.
2. Проверить `ALLOWED_HOSTS`.
3. Открыть `/nonexistent/`.
4. Проверить страницу и HTTP-статус.
5. Вернуть `DEBUG=True` для разработки.

При включённой отладке неизвестный URL показывает
техническую страницу Django.
