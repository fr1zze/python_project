# Формы Django в проекте командировок

Цель работы — использовать Form и ModelForm для пользовательского ввода,
проверки данных, создания и редактирования связанных записей, отмены заявки
и загрузки изображения. Примеры Roomly адаптированы к сотрудникам и командировкам.

## Реализация

Существующая RequestFilterForm обрабатывает GET-параметры списка. Поля
проверяются через is_valid, для ORM используется cleaned_data. При ошибке
форма показывает сообщения, список остаётся пустым. Сортировка ограничена
разрешёнными полями; пагинация сохраняет остальные параметры.

TravelRequestForm наследуется от ModelForm и явно задаёт доступные поля.
Сотрудник и бюджет относятся к TravelRequest, дополнительные поля — к Trip.
Метод save сохраняет поездку, заявку и согласование в transaction.atomic.
Создание выполняется без instance, редактирование — с существующим объектом.
Редактирование сохраняет идентификаторы заявки и поездки и текущий статус.

clean_start_date проверяет дату начала. Новая дата в прошлом запрещена;
прежняя дата исторической поездки может сохраняться без изменения.
clean проверяет поля Trip и бизнес-правила: бюджет и пересечения с другими
одобренными поездками сотрудника. Текущая заявка исключается через exclude(pk).
Отменённые и отклонённые заявки не блокируют даты, заявки на рассмотрении
не резервируют сотрудника. Новая заявка всегда создаётся на рассмотрении.

Ошибки отдельных полей, общие ошибки и подсказки выводятся в общем шаблоне
формы. При неверном POST форма остаётся связанной с отправленными данными.
Даты отображаются через DateInput, цель — через Textarea, поля используют
классы Bootstrap. В пустой форме даты по умолчанию равны текущей дате.

Метод TravelRequest.cancel меняет статус согласования на CANCELLED без
удаления данных. Представление отмены принимает только POST. Создание,
редактирование, отмена и загрузка файлов используют CSRF-защиту.
Отменённую или отклонённую заявку нельзя редактировать по прямому URL;
повторная отмена и отсутствующая запись дают 404.

Employee получил необязательное ImageField photo. EmployeeForm стала
ModelForm с полями name, position, photo. Представления передают request.FILES,
HTML-форма использует multipart/form-data. Изображение хранится в
media/employees, его путь — в базе. Фотография отображается в карточке
сотрудника, а админка позволяет загружать и заменять её стандартными средствами.
Добавлены Pillow, MEDIA_ROOT, MEDIA_URL и маршруты для локальной раздачи.
Миграция employees/0003_employee_photo.py применена.

## Проверки

Успешно выполнены:

- `python manage.py check` — ошибок конфигурации нет.
- `python manage.py makemigrations --check --dry-run` — несозданных миграций нет.
- `python manage.py test` — 28 тестов.
- `python -m pytest -v -p no:cacheprovider` — 9 прежних тестов.
- `python -m flake8 . --extend-exclude=.venv` — замечаний нет.

Тесты проверяют корректные и некорректные поля, дату в прошлом, бюджет,
конфликт поездок, сохранение без дублей, отмену, освобождение сотрудника,
404 и 405, создание/редактирование/отмену с проверкой CSRF, загрузку настоящего
изображения, отказ при поддельном изображении, замену фотографии через сайт
и админку. Проверен полный откат связанных записей при сбое сохранения.
Сохранены тесты фильтрации, сортировки, пагинации, переноса данных и ORM.

Перед изменением локальной базы создана копия db-before-pr11.sqlite-backup.
Существующие 4 сотрудника, 3 поездки, 3 заявки и 3 согласования сохранены.
Тесты работают с отдельной базой и временным медиакаталогом вне проекта.
Папка tmp и памятка не создавались.

и формы заявок с валидацией и отменой через POST. Локальные реквизиты входа,
базы, резервная копия и вспомогательные файлы в коммиты не включены.

Браузер для автоматической визуальной проверки недоступен. HTTP-сценарии и
